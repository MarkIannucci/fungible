# Canvas scope

Purpose: what canvas is for, its component model, and the one open question that limits it.

## What canvas is for

A canvas is a single-scenario calculator: a few adjustable inputs and the numbers they produce, generated by the agent from a natural-language question and pre-filled with your real data. It's the catch-all so the core screens don't grow a "mortgage tab", a "payoff tab", a "coast-FIRE tab", etc. If a question is "what if I…", it's a canvas.

## Component model

Source of truth: `core/canvas-spec.ts`. A `CanvasSpec` is a `title` plus an ordered list of elements:

| Element | Renders as |
|---------|-----------|
| `section` | a bold header (e.g. "INPUTS", "RESULTS") |
| `text` | a dim line — assumptions, caveats, data sources |
| `dial` | an adjustable input: `key`, `label`, `default`, `step`, optional `min`/`max`, `format`, `hint`. Adjusted with ← → in both surfaces. `format` includes a `toggle` variant (boolean, on/off), a `select` variant (enum: value is an index into an `options` array, cycled with ← →), and (Effort A) a `year` variant — a calendar year rendered as-is (e.g. "2035"), distinct from the existing `years` *duration* format ("5 yr"). A `year`-format dial is the typical driver for `sum_active` (below). |
| `output` | a computed row: `label`, `expr`, `format`, optional `color` and `signed`. |
| `list` | (Effort A) a named, homogeneous group of `ListRowDef` rows: `key`, `label`, plus the rows. One list per category — e.g. "Recurring expenses" and "Income streams" are separate lists, not one mixed list with a type tag; categories compose afterward through output `expr` references (a later output subtracts `total_expenses` from `total_income`). |
| `table` | (Effort B) a computed grid built from the shared `ProjectionDef` schema: `label`, `driver` (the key of an existing `year`-format dial), `series` — one or more `{ label, expr, format, color?, signed? }`. Renders one column per series, one row per year from the driver dial's `min` to `max`. |
| `chart` | (Effort B) the same `ProjectionDef` schema, rendered as a chart instead of a grid. GUI: a real `Recharts` `ComposedChart`, reusing the exact `chartTheme` recipe already used by the Net Worth/Trends screens, plus the click-a-point-to-set-the-dial interaction already live in `Trends.tsx`. TUI: a one-row Unicode sparkline (`▁▂▃▄▅▆▇█`) plus a plain numbers line — about one row of terminal space, not a multi-row rendering problem. |

- **Dials pre-fill from live data.** The generator is handed the household's income, expenses, surplus, cash, brokerage, retirement, debt, net worth, and ages, and is told to seed dial defaults from them.
- **`expr` is arithmetic only.** A safe recursive-descent evaluator — no `eval`, no `Function`. Grammar: number / `Infinity` literals, dial keys, `+ - * /`, unary `+/-`, parentheses, comparisons, ternary, and `Math.{pow,log,abs,round,floor,ceil}`. No other identifiers, no cross-references between outputs. Unknown identifiers and anything off-grammar evaluate to `NaN` and render as `—`.
- Outputs re-evaluate live as dials move.
- **`visible?: string` (any element).** An optional condition, evaluated with the same `expr` grammar against current dial values, that hides the element when it evaluates falsy. Fails open on error (a bad expression leaves the element visible rather than silently dropping it). Lets a canvas show/hide a dial or output based on another dial — e.g. a "include pension?" toggle revealing a pension-amount dial.
- **`binding?: string` (dials only).** An optional reference into a closed set of ~12 named live-data values (e.g. `net_worth`, `cash_balance`, `monthly_income_12mo_avg`, `self_age`), resolved against a live query when the canvas is loaded or reopened. If the binding can't be resolved, the dial falls back to its hardcoded `default`. Resolution happens only at load time, never mid-session — it never overwrites a value the user has already adjusted. This is what fixes deficiency #10 (stale baked-in defaults on reopen): a canvas opened weeks after generation shows current income/cash/net-worth, not creation-day numbers.

## Resolved: canvas grows a list/timeline element (Effort A)

Canvas cannot express a **dynamic or interactive list** — "add an expense row", "remove this one", "this cost starts in 2031". Every dial is a fixed scalar chosen at generation time. That blocked the named case: journey 3's "a real early-retirement plan with a mortgage payoff and college costs can't be built" ([`journeys.md`](journeys.md)).

Decided 2026-09-17 (see `decisions.md`): option **(a)** — grow canvas a real list/timeline element — over (b) a separate dated-cash-flow tool or (c) accepting the limit. Below is the concrete row shape and aggregation scope core/tui/gui build against, sanity-checked against journey 3 and against Thomas's own life-plan numbers (two kids starting college roughly two years apart, a target cash date, no fixed mortgage-payoff year yet named — all fine, none require a field beyond what's below).

The `toggle`/`select` dial formats, `visible`, and `binding` (issue #145 Phase 1) remain orthogonal — they don't add repetition, add/remove, or row aggregation, and this decision doesn't retroactively make them part of it.

### The row shape

```
ListRowDef { id: string, label: string, amount: number, startYear?: number, endYear?: number }
```

`id` plus four fields, both date bounds optional. Deliberately not richer:

- **`id`** — added so a row survives edits and reloads addressed by something more stable than list position, needed once row edits persist (below). Assigned when the row is created.
- **`amount` is signed and monthly**, matching the app-wide unit convention (`definitions.md`) and existing dial/binding values (`monthly_income_12mo_avg`, etc.). Negative = outflow, positive = inflow. No separate `type: income|expense` field, no per-row period/unit field — an annual college bill of $30k is entered as amount `-2500`, the same conversion the generator already does when it seeds dial defaults from live monthly data today.
- **`endYear` is optional, defaulting to `Infinity`** (already a legal literal in the `expr` grammar) — covers an open-ended flow like a pension with no modeled end, without a separate "ongoing" flag.
- **`startYear` is optional too** — an unbounded lower edge for a flow that's already running with no meaningful "start," mirroring `endYear`'s treatment of the open-ended top. Neither bound should have to be backfilled with a fake value just to satisfy the type.
- **One-time cost = `startYear == endYear`.** No boolean/mode field. A single lump-sum payment is a row active for exactly one year; the aggregation (below) treats it identically to a multi-year recurring row — it just has a window of one.
- **No multiplier/count field for "N kids in college."** One row per kid. Two kids starting college in different years (the common case — siblings a few years apart, e.g. Thomas's own two at ~13 and ~15 years out) need different `startYear`/`endYear` pairs; a multiplier only works if every instance shares one window, which the journey's actual shape doesn't guarantee. Two labeled rows ("College — [kid]") is also what reads clearly in a TUI list with no room for a nested structure.
- **One list per homogeneous category**, not one mixed list with a type tag — "Recurring expenses" and "Income streams" are separate `list` elements. Categories compose afterward via Effort B's output-key references rather than a per-row type field.

Walking journey 3 through this shape: mortgage payoff is one row, `label: "Mortgage payment"`, `amount` negative, `startYear` = this year (or origination year), `endYear` = the payoff year — after which it drops out of the active sum on its own, no separate "payoff" concept needed. Each kid's college is its own row with its own window. A pension or other late-life income is a row with `endYear` omitted. That's the full vocabulary the named scenario needs.

Row-level `visible` and per-row `binding` are explicitly deferred, not part of this effort. The list *element* itself does gain `visible`, and its condition can read list data (e.g. a row count) alongside dial values when evaluated — rows are static input data, closer to a dial than to a derived output, so that access doesn't stretch the `expr` model the way reading another output's value would.

### Aggregation: two narrow builtins, not a general filter

An unconditional sum-over-all-rows (no date filtering) is not enough for v1, and Effort A should not ship without more than that. The entire premise of journey 3 is time-dependent — "what changes when the mortgage ends," "what happens while both kids are in college at once" — so a total that ignores `startYear`/`endYear` doesn't answer the question the journey is named for, even though listing and editing the rows would already be a UI improvement on its own.

The minimal fix, sized to core's ask to keep the `expr` grammar extension small: **`sum_active(list_key.amount, year_expr)`**, the sum of `amount` over the list's rows whose `[startYear, endYear]` window contains `year_expr`. `year_expr` is normally a plain dial — a `year`-format dial the user scrubs with ← → exactly like every other dial today, so canvas's existing interaction model (move a dial, outputs re-evaluate live) carries the whole feature with no new UI concept. Alongside it ships **`count(list_key)`**, an unconditional row count with no date filtering — for a plain "how many rows" output without composing a `sum_active` call. Two builtins, both bounded and specific: no general boolean predicates, no cross-row references, no general query language. Do not generalize further in this cut — no `min()`, `avg()`, or similar; add one only if a later scenario actually needs it.

Deferred to a later phase, not blocking Effort A: multiple simultaneous list elements aggregated together, and list rows that themselves reference dials (e.g. an amount that scales with an inflation dial). Table and chart output (below) are now addressed, as Effort B.

### Persistence: the first canvas state that survives navigation

Every other canvas interaction — moving a dial, a `visible` branch flipping — is ephemeral view state: it resets on reload or reopen, by design. List rows are the exception: add/remove/edit of a row persists, surviving navigating away and reopening the canvas. This is a deliberate product decision, not an implementation shortcut — adding a mortgage-payoff row or editing a college-cost estimate reads as data entry, not calibration, and losing it on navigation would be a real regression in trust (see `decisions.md`, 2026-09-17). It's the first canvas interaction that writes back to saved history rather than just adjusting live view state.

Read this narrowly: it's an exception granted to list rows specifically, on the strength of that data-entry-vs-calibration distinction — not a precedent that canvas state in general should start persisting. Dial adjustments stay ephemeral.

Rendering follows each surface's existing idiom rather than a new one: TUI flattens list rows into the existing ↑↓ cursor list (same precedent as `Settings.tsx`'s children/spouse list); GUI renders inline-editable rows with no modal, consistent with canvas's existing direct-manipulation model. Neither is a new navigation or interaction mode.

## Resolved: canvas grows table and chart output (Effort B, issue #145)

The last two of the original ten deficiencies were chart and tabular output, both deferred through Phase 1 and the list primitive because there was nothing to iterate over. Now that lists, `sum_active`/`count`, and `year`-format dials exist, the blocking case is the one line left in journey 3's friction: *"Canvas outputs are arithmetic over scalar dials; anything iterative (year-by-year projection) has to be pre-baked into one `expr`."* Concretely: "am I ever underwater between now and retirement" or "what's the worst year with both kids in college at once" today means scrubbing a `plan_year` dial across 20 one-at-a-time steps and remembering each result — the exact kind of friction `canvas-scope.md`'s growth bar exists to catch, not a nice-to-have.

**Decision: ship both `table` and `chart` in this cut**, sharing one `ProjectionDef` schema (`label`, `driver`, `series`). The table case for shipping is unchanged from the original recommendation and is the stronger of the two: it answers the named question directly — scan a column for the first negative number, or the max, at a glance, with exact figures. Precision matters here (a financial decision, not an impression), which a chart alone would trade away; table is what actually resolves journey 3's named friction. Chart was initially recommended deferred on the assumption that a terminal chart (TUI) and a real chart (GUI) were different, materially riskier rendering technologies to keep in parity. Direct review with tui and gui found that assumption wrong on both sides: GUI already has Recharts wired up for the Net Worth/Trends screens, and Effort B's chart reuses that exact `ComposedChart`/`chartTheme` recipe plus the click-to-jump interaction already live in `Trends.tsx` — no new charting library, no new pattern. TUI's chart is a single-row Unicode sparkline (`▁▂▃▄▅▆▇█`) plus a plain numbers line, about one row of terminal space — not the multi-row rendering problem the original assessment pictured. With both sides this cheap, there was no remaining reason to hold chart back once table was already justified.

The TUI-sparkline-vs-GUI-real-chart split is a deliberate, sanctioned divergence, not a parity gap: `parity.md` already lists "charts vs. ASCII bars" as an acceptable per-surface rendering difference, since parity is about same data and same journey outcome, not identical rendering technology (see [`parity.md`](parity.md)). Table, by contrast, renders as the same grid on both surfaces — no divergence to sanction there.

**Driving dial: restricted to `year`-format only, not any bounded numeric dial.** The one named use case — and `sum_active`'s existing convention — is projecting across years. Nothing in journey 3 or elsewhere names a need to iterate a table or chart over a percent or dollar dial's range. Generalizing now would be scope nobody asked for; this project's convention is to ship the narrow thing that resolves the named need. Revisit if a scenario later names a real sensitivity use (e.g. "total interest paid across a range of mortgage rates").

**Point handling: three layers, not a single number.** The original recommendation was a single cap (40 recommended, 50 ceiling), sized to Thomas's own horizon — kids currently 5 and 3, college starting roughly 13 and 15 years out, cash-to-$160k around 2029, a realistic planning canvas on the order of 20-30 years. That guidance stands, but core/tui/gui's build reconciles it into three layers rather than one number: (1) **40-step prompt guidance** for the generator, unchanged from the original recommendation — the target for what a sane canvas should ask for; (2) a **120-point runtime safety cap** as a backstop, with resample-to-fit rather than truncation when a driver dial's range would exceed it — this is a hard ceiling against a pathological dial range, not a target, and it never cuts off the horizon, only reduces resolution across it; (3) **TUI downsamples independently** on top of that for its own display budget (a sparkline row and a non-cursor table both have real terminal-width/height limits regardless of how many points core hands back). Read 40 and 120 as different things answering different questions — authoring guidance vs. a runtime ceiling — not as a contradiction.

## When canvas should grow vs. stay finite

Grow it only when **all** of these hold:

- The missing capability blocks a journey in [`journeys.md`](journeys.md), not just a nice-to-have.
- The new primitive is expressible in the TUI with keyboard-only interaction without feeling bolted on.
- It generalizes — a list primitive would serve several scenario types, not just one.
- The `expr` grammar extension stays safe (no arbitrary evaluation) and small.

Effort A above is the one exception recorded as meeting this bar. Any future ask to grow canvas further should be checked against the same four criteria, not assumed to inherit Effort A's approval.
